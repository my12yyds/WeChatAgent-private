# 开发与迭代流程

本文是本仓库改动的通用操作指南。每个版本先核对仓库状态和真实脚本；不要假定另一份安装目录或运行快照就是源码。

## 1. 找到正确的修改位置

1. `git status --short --branch` 确认分支和未提交内容。先保护已有改动，不要用重置或覆盖命令清理工作区。
2. 阅读根目录 `AGENTS.md`（若存在）、本文件、`docs/PROJECT_LAYOUT.md` 和目标模块专题说明。
3. 从真实入口向下追踪：控制台在 `public/console/`，服务与生命周期在 `scripts/`，共享业务模块在 `packages/`，微信/DSH 组件在 `components/`，插件在 `optional-extensions/` 或 `examples/plugins/`。
4. 先用 `rg` 搜索调用方、配置字段、API 路由和相似测试。只改当前实际调用的实现；历史兼容目录和 `release/` 副本不是默认编辑入口。
5. 配置、权限和数据迁移类改动，先确认现有配置如何载入、旧格式如何兼容、失败时数据会不会被覆盖。

## 2. 把需求写成可验收的改动

开始实现前，简短记录：

- 用户遇到的问题及复现条件。
- 改动涉及的模块、数据和权限。
- 期望行为与明确不做的行为。
- 至少一个正常路径和关键失败路径的验收条件。
- 是否需要更新用户文档、配置示例、插件清单或升级说明。

跨模块或高风险功能先写设计说明；小而局部的修复可在 PR 描述中记录以上信息。

## 3. 实现约定

- 维持模块边界，不为同一功能复制第二套入口或旧实现。
- 配置字段设置安全默认值，验证输入，并保留已有用户设置；权限必须清楚可见且按最小范围生效。
- I/O、外部 API、子进程与队列操作设置合理超时，明确取消和失败状态。
- 对发送、支付式副作用、文件覆盖等不可轻易重做的动作，使用幂等标识并区分“未提交”“已提交但回执未知”，避免盲目重试。
- 日志用于排错，不记录令牌、Cookie、密钥、完整消息或不必要的身份数据。
- 延续项目许可证与上游版权声明；新增第三方资源或依赖时更新来源和许可证记录。
- UI 文案说清楚开关影响、权限范围和未经验证的假设；不用概率或保证替代证据。

## 4. 验证改动

只运行与修改范围匹配的现有检查；不要添加耗时或会触发真实账号副作用的检查，除非任务要求并且有隔离环境。

1. 检查 `package.json` 中实际定义的 scripts，以及 `scripts/` 中真实存在的验证脚本。
2. 运行目标模块单测/检查，再运行相关回归；记录命令和结果。
3. 修改 UI 时检查默认、暗色、窄窗口和键盘/无障碍状态；验证按钮保存、取消、错误和页面刷新路径。
4. 修改配置时用脱敏的旧/新 fixture 验证迁移和保留行为。
5. 修改发送或工具执行时只用模拟/隔离环境；真实账号端到端操作应单独说明并避免重复副作用。
6. 运行仓库当前可用的隐私检查。发布构建应在隔离目录中完成，并保存构建版本和验证范围。

如果某项验证不能运行，记录原因和未覆盖范围，不把它标记为通过。

## 5. 完成改动

- 更新专题文档、README 入口或 `RELEASE_NOTES.md`，仅描述已实现且已验证的行为。
- 查看 `git diff --check`、`git diff --stat` 和完整 diff；确认没有本机配置、状态、日志、截图、二进制或用户插件。
- 确认许可证、配置模板、测试和文档一起纳入变更。
- 提交信息用简短中文或 Conventional Commit，聚焦一个目的，例如 `fix: 修复多表情发送队列`。
- 需要发布时遵循发行版文档；先同步远端并检查冲突，不使用强推覆盖他人提交。

## 6. 问题报告最低信息

提供应用版本、Windows 版本、前置条件、复现步骤、期望与实际结果、脱敏后的相关日志。不要附微信数据库、Cookie、授权令牌、聊天导出、完整用户目录或含个人信息的截图。无法确认安全脱敏时，先摘录必要错误行。
